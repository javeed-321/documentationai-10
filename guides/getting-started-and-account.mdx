# Overview

# **Introduction&#xA0;**

This section walks through the customer-facing statements describing the security and compliance posture of the ARMOR Discovery + Remediation platform. It draws from the platform’s architectural design principles, data flow controls, AI governance framework, and audit capabilities. 

# **Architecture & Data Sovereignty&#xA0;**

ARMOR Discovery is built on a modern, cloud-native microservices architecture where security, privacy, and data residency are foundational design principles. 

The platform is structured across two distinct environments. The Seclore-managed cloud hosts all backend services, the control plane, the AI/semantic analysis engine, and the catalogue store. The customer enterprise environment hosts only the on-premise surface connector, the sole component requiring deployment within the customer boundary. The SaaS surface connector is fully managed by Seclore, requiring no deployment effort from the customer. 

Current cloud infrastructure is hosted on AWS and GCP, with multi-region support covering North America, India, and the Middle East, enabling customers to meet regional data residency requirements. 

# **Data Flow & Privacy Design&#xA0;**

## **What Data Moves and Where?&#xA0;**

Document content travels through the minimum number of channels possible and is protected at every stage of its journey. 

Configuration and credentials entered by users are transmitted over TLS and stored with disk encryption in the database. Document content is downloaded only into a temporary folder within the connector during active processing and is never persisted to the catalogue store. Immediately after categorisation is complete, the file is automatically and permanently purged. The catalogue store retains only metadata including file path, size, business category, sensitivity label, and PII/PCI indicators and never stores raw document content. 

## **Data Masking Before AI Processing&#xA0;**

Before any document content is transmitted to the AI/semantic analysis component, it passes through a data masking module embedded directly within the surface connector. This module operates before data leaves the connector boundary and performs the following: 

- Detects sensitive information such as personal identifiers, financial data, and health records. 

* Tokenises sensitive values and replaces them with format-preserving dummy equivalents — for example, a real email address is replaced with a synthetic email address that retains the format but contains no real data. 

- Ensures the LLM can still accurately classify the document without ever processing real customer sensitive data. 

This masking component is built into the connector itself and is not a separate cloud-side service, giving customers a strong privacy guarantee at the point closest to the data. 

## **Data Residency&#xA0;**

AI processing is region-locked. Document content is always routed to the semantic analysis service deployed in the same region as the surface connector and data source. Content originating in India, for example, is processed only by the India-region semantic analysis instance and does not leave that region under any circumstance. 

## **Privacy & Security of Auditing and Usage Data&#xA0;**

Privacy and security of auditing and usage data are governed by strict controls defined in the privacy design documentation shared with legal. Seclore operators are granted only least-privilege access to audit and telemetry data, and any access to detailed information requires a formal approval process. Product metrics and usage insights are anonymized, ensuring that user identities are not visible to Seclore. Additionally, all audit logs and telemetry data are protected through encryption both at rest and in transit, maintaining a high standard of data security. 

# **Encryption Standards&#xA0;**

ARMOR Discovery applies encryption consistently across all data states and transmission channels. 

| **Layer**                              | **Control Applied**                                    |
| -------------------------------------- | ------------------------------------------------------ |
| Data in transit - UI to backend        | TLS                                                    |
| Configuration sync to connectors       | MQTTS (TLS-equivalent over message queue)              |
| Temporary file storage on connectors   | Disk encryption on processing hosts                    |
| Catalogue and metadata database        | Disk encryption at rest                                |
| Connector to AI service communication  | TLS                                                    |
| Credential storage                     | Disk encryption + application-layer encryption add-on  |

# **Authentication & Access Control&#xA0;**

The platform uses SSO-based authentication via standard OIDC and SAML protocols, integrating with existing customer identity providers including Microsoft Entra ID, Google, Okta, and Policy Server. No separate user repository is maintained within the discovery system. 

Role-based access control is available within the product, allowing organisations to define administrators, editors, and viewers. Only users with appropriate privileges are permitted to initiate or enforce remediation actions such as classification or labelling. 

# **On-Premise Connector Security Posture&#xA0;**

The on-premise surface connector is designed to be a non-invasive extension of the customer environment, with the following security characteristics: 

- Delivered as a hardened Docker package running on a Linux VM inside the customer network. 

* Uses outbound-only HTTPS and MQTTS channels, no inbound ports or listening sockets are required, meaning no inbound firewall rules need to be opened. 

- Repository credentials and configuration are held in memory only during active scanning and do not persist to disk. 

* Supports SMB 2 and SMB 3 protocols. The legacy CIFS/SMB 1 protocol is not supported due to its deprecation by Microsoft and associated security vulnerabilities. 

- Multiple connector instances can be deployed within a customer environment where file servers exist across isolated network segments or subnets. 

# **AI Model - Privacy & Governance&#xA0;**

## **Self-Hosted Models Only&#xA0;**

ARMOR Discovery uses only self-hosted LLMs. No calls are made to external managed AI services such as OpenAI or other third-party cloud AI APIs. The model is hosted entirely within Seclore-controlled infrastructure, ensuring that no customer data leaves Seclore’s environment during AI processing, and that there is no dependency on external AI provider data handling or retention policies. 

## **No Training on Customer Data&#xA0;**

Customer document content is never used to train or fine-tune the AI model. The platform operates exclusively on pre-trained model weights. Any future use of customer data for model improvement would be strictly opt-in and would require explicit customer consent. This is a deliberate privacy-by-design decision. 

## **Temporary Content Handling&#xA0;**

Document content sent to the semantic analysis component is not permanently stored at that layer. It is retained only for the duration of the categorisation process and is immediately discarded upon completion. No content persists beyond the active processing window. 

## **Model Governance & Prompt Control&#xA0;**

All prompt versions are tracked and audited. Every prompt change is versioned, attributed to the individual who made it, and benchmarked against a controlled dataset before being deployed to production. Prompt changes are access-controlled and fully auditable. 

Our DSPM product treats prompts as governed policy artifacts. Prompt updates follow a structured authorization workflow, are version-controlled, and are rigorously evaluated against controlled datasets. This approach ensures that classification behavior remains consistent, explainable, and auditable across all deployments.

## **&#xA0;Summary&#xA0;**

- Our LLM operates in an isolated environment with no external connectivity, eliminating the risk of data exfiltration through prompt injection. 

* We treat prompts as policy artifacts — reviewed, approved, version-controlled, and fully auditable. 

- All outputs are schema-validated, ensuring that any injected instructions are ignored. 

* Every classification decision is traceable to a specific prompt version, ensuring full auditability. 

# **Classification & Remediation Governance&#xA0;**

## **Label Architecture&#xA0;**

The platform operates with three distinct label types, each serving a different purpose in the classification lifecycle. 

Discovery labels are the AI’s prediction of the appropriate sensitivity classification for each file. These exist only within the ARMOR catalogue and are not written into the file itself. They are available for consumption by DLP systems or other downstream tools. 

DAC labels (Seclore classification) and Microsoft Purview labels (MPIP) are enforcement labels that are written directly into the file metadata as a remediation action. These are applied only when the customer has the corresponding labelling system in place and an explicit remediation action is triggered. 

## **Remediation Behaviour&#xA0;**

All remediation actions are executed asynchronously. This design ensures scalability and resilience — if a remediation system is temporarily unavailable, the action is queued and executed once the system recovers, avoiding failure states. Edit-level access to the repository is required for any remediation action. Discovery-only scanning requires read-only access. 

Where a file is locked or being actively edited, the system applies a retry mechanism with a configured limit. If remediation cannot be completed within that window, the status is recorded as failed in the catalogue and the reason is available in the exported report. 

## **Classification Override Logic&#xA0;**

The platform applies a governance rule that gives precedence to user-driven classification over system-driven classification. If a user has explicitly classified a file, the system will not override that classification, regardless of its own prediction. If a file has only been classified by the system, the system may update its own prior classification as its analysis improves. 

Discrepancies between AI-predicted classification and existing user-applied classification are captured in the catalogue data export, with separate columns for each, allowing analysts to identify and investigate differences. 

# **Audit, Monitoring & SIEM Integration&#xA0;**

## **Audit Log Coverage&#xA0;**

The platform captures structured audit events across the following activity categories: 

**Currently in scope:** User logins, policy changes, and repository configuration updates, sensitivity label changes, remediation actions including classification events

**Next phase:** Prompt governance logs, and AI consultation records. 

All audit events are captured through an asynchronous event pipeline and are structured for easy forwarding to third-party systems. 

## **SIEM & BI Integration&#xA0;**

Audit logs and catalogue data can be forwarded to SIEM platforms such as Splunk, Microsoft Sentinel, and Radar, as well as BI tools such as Power BI and Tableau. Native SIEM forwarding capability is targeted for availability within the near-term product roadmap. The same underlying technology pipeline supports both SIEM integration and BI export, using time-series structured event data. 

## **Catalogue Data Export&#xA0;**

All catalogue data, including file-level metadata, AI-predicted classifications, existing classifications, sensitivity indicators, and data type attributes, is exportable as a CSV. The export contains richer metadata than is visible in the UI and is intentionally designed to allow enterprises to perform their own analysis using preferred tools. This supports use cases such as compliance project reporting, DPDP or GDPR readiness assessments, RBI audit preparation, and custom risk dashboards.
